# 阶段六真实失败 Session 筛选报告

## Summary

本次测试按“先证明 Baseline 错误可稳定复现，再调用 Jev”的预注册顺序检查本机 DSH Session。初始存储包含 56 条 Session 投影、18 份原始 Session 文件，其中只有 7 份具有可重放事件；这 7 份均没有“主模型给出错误结果，随后由用户或客观证据纠正”的完整记录。后续历史缺陷重放对三个有效候选各执行两次 Baseline，六次均正确，因此仍没有案例达到至少 2/3 次错误的准入条件，也没有调用 Jev。

## 筛选方法

- 只检查本机 Session，不上传对话内容，不在报告中保存用户文本、模型回答、工具参数或文件路径。
- 使用摘要标识、事件数量、消息来源、工具调用数量和 Jev 事件数量区分 Session；摘要标识不能还原原文。
- 合格案例必须同时包含错误发生前的完整上下文、可验证的错误判定、后续纠正证据，以及不依赖已变化外部状态的重放条件。
- 先要求同一冻结检查点的 Baseline 三次运行至少错误两次；只有满足该条件的案例才允许进入 Shadow 和 Advisory。
- 测试提示中出现“错误”“失败”或“排查”等词不等于主模型发生错误，不能单独作为候选证据。

## 筛选结果

| 层级 | 数量 | 结果 |
|---|---:|---|
| Session 投影 | 56 | 只有标题和统计的投影不能重建错误检查点 |
| 原始 Session 文件 | 18 | 11 份仅含初始化记录，不能重放任务 |
| 具有任务事件的 Session | 7 | 进入结构化检查 |
| 重复评估运行 | 4 | 四份直接用户输入摘要相同，属于既有评估任务，不是真实失败案例 |
| 其他可重放 Session | 3 | 包含连接、工具或评估流程，但没有后续纠正主模型结论的证据 |
| 合格真实失败候选 | 0 | 未进入 Baseline 稳定性复测 |

七份可重放 Session 都有完整 turn 结束记录。四份重复运行各包含三个用户 turn、71 次工具调用和相同的直接用户输入摘要；另外三份分别包含连接诊断、显式 `jev_decide` 调用或已有阶段六任务。关键词扫描发现的是任务描述中的失败条件或诊断请求，没有发现明确否定前一条模型结论的用户消息。现有投影缓存不能替代已经缺失的原始事件。

## 历史缺陷 Baseline 重放

本轮使用修复前代码和后续回归测试作为客观纠正证据，候选覆盖自动决策 deadline、Provider 成功后的输出用量后置拒绝，以及在线 Session 汇总语义。每个候选先运行两次；连续两次正确后按提前停止规则淘汰，不运行第三次。

| 候选 | 有效 Baseline | 正确 | 错误 | 结果 |
|---|---:|---:|---:|---|
| 自动决策端到端 deadline | 2 | 2 | 0 | 淘汰 |
| 输出用量后置拒绝 | 2 | 2 | 0 | 淘汰 |
| Provider、简报和注入汇总语义 | 2 | 2 | 0 | 淘汰 |

浏览器配置生命周期候选的两次运行读取了冻结目录之外的修复版源码，因此不具备独立性并全部作废。另有两次运行使用了错误工作目录并在完成前中止。作废运行不进入准确率统计，但其 API 用量仍计入成本。

| 运行组 | 运行 | 输入 token | 输出 token | 总 token | Cache-read token |
|---|---:|---:|---:|---:|---:|
| 有效 Baseline | 6 | 268,748 | 45,458 | 314,206 | 1,512,831 |
| 读取修复版后作废 | 2 | 236,795 | 43,664 | 280,459 | 7,308,416 |
| 错误工作目录后中止 | 2 | 80,099 | 7,975 | 88,074 | 629,504 |
| 全部已启动运行 | 10 | 585,642 | 97,097 | 682,739 | 9,450,751 |

六次有效运行全部正确，合格失败候选仍为零。评估没有进入 Shadow 或 Advisory，Jev 调用为零。自主仓库搜索还产生大量工具 step 和上下文 token；后续筛选必须使用预提取的最小代码切片和外部评分器，并为单候选设置 token 上限。超出上限的运行应停止，不能继续用完整仓库搜索积累失败样本。

## 验收结论

| 条件 | 结果 | 说明 |
|---|---|---|
| 从真实 Session 找到可验证错误 | 未通过 | 合格候选为 0 |
| 历史缺陷形成稳定 Baseline 错误 | 未通过 | 三个有效候选均为 2/2 正确 |
| Baseline 错误至少稳定复现 2/3 | 未执行 | 没有候选可进入复测 |
| Jev 建议方向与纠正证据一致 | 未执行 | 没有发起 Jev 调用 |
| Advisory 连续两次修正错误 | 未执行 | 没有进入 Advisory |
| Advisory 降低无效探索或总 token | 未执行 | 没有形成配对样本 |
| 避免无证据 Jev 调用 | 通过 | 没有候选通过 Baseline 条件，Jev 调用为零 |
| 控制 Baseline 筛选成本 | 未通过 | 十次已启动运行共消耗 682,739 token，其中四次作废 |

本轮结果表示“证据不足”，不表示 Jev 有效或无效。阶段六的产品价值条件仍未通过，Advisory 不应被描述为能够提高准确率或节省 token。

## 下一轮数据要求

下一次评估需要先积累真实失败记录。发现主模型错误时，用户可以在纠正消息首行写 `/jev-failure <错误标签>`。插件会在原始 Session 中追加不含正文的 `plugin:dsh-jev/failure-candidate`，引用上一条 Assistant 检查点和当前纠正消息；同一检查点只计一次，也不会触发 Jev 调用。评估人员还要确认纠正证据足以判错，并确认外部文件与服务状态可冻结或可用本地夹具替代。

积累至少两个合格案例后，每个案例先运行三次 Baseline。只有错误至少出现两次，才各运行一次 Shadow；Jev 方向与纠正证据一致后，再运行一次 Baseline 确认和两次 Advisory。准确率与 token 效率分别判定，不能用节省 token 抵消错误，也不能用一次修正掩盖总成本增加。

当前插件配置页显示候选数量和是否达到两个不同 Assistant 检查点的数量门槛。该门槛只允许开始人工资格复核，不会自动发起付费测试。
