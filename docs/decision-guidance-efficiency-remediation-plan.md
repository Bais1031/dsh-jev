# Jev 决策增强调用效率修复计划

## Summary

当前自动决策链路可以触发 Jev、生成简报并在 Advisory 模式注入主模型，但早期真实测试显示简单任务会产生无效调用。两次未注入的简单任务合计消耗 2,545 Jev token、增加约 4.04 秒等待，并且发送内容包含与用户问题无关的运行时文本。本计划先修复输入范围和调用前筛选，再处理节点识别、协议重叠、预算退避和真实对照评估。

## 当前结论

真实 Session 记录确认，两次“未收到决策简报”均由置信度低于 `0.5` 导致，不是 Provider 超时或网络失败。登录故障选择题消耗 1,275 Jev token，置信度为 `0.33`；数据库迁移题消耗 1,270 Jev token，置信度为 `0.36`。两次结果均未进入主模型。

当前阈值只能在 Jev 返回后决定是否注入，不能减少已经发生的调用。降低阈值会增加低质量简报注入，提高阈值仍会支付相同 Jev 成本。插件必须在调用 Jev 前排除低价值节点，并缩小发送内容和问题集。

## 问题优先级

| 优先级 | 问题 | 直接影响 |
|---|---|---|
| P0 | Jev 输入包含 DSH 时间、时区等运行时文本 | 扩大外发范围，增加 token，并可能干扰判断 |
| P0 | `direction-selection` 仅凭“方案、选择、还是”等词触发 | 简单任务产生纯额外成本 |
| P0 | 中文缺失信息识别不完整 | 任务进入错误节点并使用不合适的问题集 |
| P1 | `recommendedAction` 与 `focus` 选项语义重叠 | 概率分散，整体置信度偏低 |
| P1 | 整份简报使用动作与方向置信度的最小值 | 高价值字段可能因另一个字段不稳定而全部丢弃 |
| P1 | 缺少 Session token 预算和连续低置信度退避 | 连续无效调用仍会继续消耗 token |
| P2 | 页面没有显示跳过原因和剩余预算 | 无法快速区分节流、退避和未命中节点 |

阶段必须按顺序验收。上一阶段未通过时，不进入下一阶段，因为后续 token 和置信度数据会受到错误输入或错误节点影响。

## 阶段 1：隔离 Jev 输入

### 目标

自动调用只发送本次真正接纳的用户文本，以及用户明确启用的上一步工具结果摘录。DSH 时间提示、时区提示、其他插件上下文、已有 Jev 简报和运行时辅助消息不得进入 Jev 请求。

### 修改范围

- 为参与自动分析的消息来源建立明确允许列表，不再合并所有 `UserMessage` 文本块。
- 保留当前字符上限、凭证模式检测和工具结果摘录限制。
- `plugin:dsh-jev/decision-request` 继续保存发送给 Jev 的精确有界请求，使 Session 可以重建辅助调用。
- 测试提示中的“是否收到简报”属于用户原文，不由插件擅自删除；正式评估通过 Session 记录和页面状态判断注入结果。

### 验收条件

- 输入测试同时提供用户消息、时间上下文、其他插件消息和旧 Jev 简报，记录中的 `request.state.content` 只包含允许的用户文本。
- 启用工具结果摘录时，仅允许紧邻上一步的有限纯文本；工具参数、二进制内容和疑似凭证仍被排除。
- 真实测试不再在 Jev 请求中出现 `Time sampled`、`Browser time zone` 或 `Elapsed since`。
- 发送字符数和 Jev input token 不高于同一用户文本的现有实现。

## 阶段 2：增加调用前价值筛选

### 目标

插件只在 Jev 可能减少后续分析步骤、工具调用或错误方向时付费调用。短而明确的一步选择、改写、翻译和格式转换不调用 Jev。

### 修改范围

- 将节点分成两类：`tool-recovery`、`progress-check`、`pre-conclusion` 属于已有执行证据的高价值节点；`task-intake`、`missing-information`、`direction-selection` 属于需要额外筛选的早期节点。
- 为早期节点增加可配置的确定性筛选条件。条件至少考虑有效用户字符数、多约束信号、候选方向数量、风险词和已有 Agent step，不再只依赖单个关键词。
- 简单 `direction-selection` 在首个 step 且没有工具证据、复杂约束或风险信号时跳过 Jev。
- 不使用另一个模型判断是否调用 Jev；筛选过程必须是本地、确定性且不产生模型 token。
- 跳过操作记录无内容原因码，至少区分 `simple-task`、`insufficient-complexity`、`cooldown`、`session-call-limit`、`token-budget` 和 `backoff`。

### 验收条件

- “修复影响用户的登录故障还是开发无截止日期的新功能”不产生 Jev 调用。
- 简单翻译、改写和格式转换不产生 Jev 调用。
- 多约束方案比较、工具失败恢复和多步无进展仍能触发对应节点。
- 筛选参数通过插件配置提供，不以不可调整的部署数值写死在实现中。
- 简单任务测试集的误触发率为零；复杂任务测试集不得因筛选全部失去 Jev 覆盖。

## 阶段 3：修正节点识别

### 目标

触发器为任务选择与实际问题一致的节点，使 Jev 收到最小且相关的问题集。

### 修改范围

- 扩充中文缺失信息表达，包括“没有提供、没提供、尚未提供、缺乏、尚不清楚”等常见形式。
- 保留 `missing-information` 高于 `direction-selection` 的优先级；同时匹配“没有提供”和“还是”时选择缺失信息节点。
- 将中英文触发表达集中为可审查的固定规则，并为每个表达增加正例和反例。
- 节点判定继续记录原因码，不保存额外自由文本诊断。

### 验收条件

- 数据库迁移示例命中 `missing-information`，不再命中 `direction-selection`。
- 普通陈述中的“方案”不会在缺少选择语义时误触发方向选择。
- 每种节点均有中文和英文正例、反例及优先级冲突测试。

## 阶段 4：精简问题协议与简报投影

### 目标

减少 Jev 请求字段和说明文本，消除动作与方向的重复表达，并保留可独立使用的高置信度信号。

### 修改范围

- 重新审查 `answer` 与 `answer-directly`、`ask-user` 与 `clarify-goal`、`inspect-context` 与 `inspect-local-context` 的重复语义。
- 为每个节点定义最小问题集；不要求所有节点同时回答信息充分度、动作、方向和歧义。
- 缩短 Choice criteria，在含义不变的前提下减少重复描述。
- 评估按字段置信度生成简报：高置信度字段可保留，低置信度字段可省略；不得把不完整简报伪装成完整建议。
- 如果持久化字段或模型可见格式变化，发布新的协议版本，并保持旧 Session 记录可读。

### 验收条件

- 固定测试请求的序列化字节数和真实 Jev input token 均低于 `decision-brief-v2` 基线。
- 数据库迁移类结果可以保留高置信度的“信息不足”或“歧义高”，不会仅因方向字段不稳定而丢弃全部信号。
- 未达到字段阈值的内容不会进入主模型。
- 简报仍不包含 Jev 自由文本、隐藏推理或外部操作授权。

## 阶段 5：增加预算和退避

### 目标

一个 Session 内连续低价值结果或 Provider 故障不会无限消耗 Jev token 和等待时间。

### 修改范围

- 增加可配置的 Session Jev token 预算；已记录 usage 达到预算后停止后续自动调用。
- 分别统计连续低置信度、Provider 失败和 deadline。不同原因使用独立退避状态，不把协议低置信度误报为网络失败。
- 连续低置信度达到配置阈值后，在当前 Session 内暂停早期节点；高价值恢复节点是否继续调用由独立配置决定。
- Provider 失败使用有上限的退避；用户主动取消不进入失败退避。
- Agent 释放时清理内存状态，Session 记录保留无内容预算和退避原因。

### 验收条件

- 连续两次低置信度后，后续相同早期节点按配置跳过，且不产生 Provider 请求。
- 达到 Session token 预算后不再产生自动 Jev usage。
- 成功调用可按配置重置 Provider 失败退避，但不会重置已经消耗的 token。
- 页面和 Session 记录能够区分预算、低置信度退避、Provider 退避和普通未触发。

## 阶段 6：真实配对评估

### 目标

使用真实 Jev 和相同主模型比较修改前后成本，并判断 Advisory 是否提高关键决策质量或减少无效探索。

### 测量方法

- 固定主模型、reasoning effort、插件配置和任务集。
- 每个任务在新的 Session 中分别运行一次 Baseline、Shadow 和 Advisory；只对模式结论不同、置信度接近阈值、Provider 故障或 token 异常的任务定向复测，核心 18 次、总量最多 26 次。
- 任务集分别覆盖简单不触发、复杂方向选择、信息不足、工具失败恢复、进展停滞和高风险操作。
- 预先定义任务成功、关键决策正确和无效工具调用的判定规则。
- 报告主模型 token、Jev token、总 token、Jev 延迟、Agent step、工具调用、重复工具调用、触发和跳过原因。
- `pnpm eval` 继续用于合成管线验收，不能替代真实 Provider 证据。

### 验收条件

- 简单任务的 Jev 调用数相对当前基线下降，且主模型任务成功率不下降。
- 修改后的有效 Jev 请求在相同任务上的平均 input token 低于修改前基线。
- Advisory 成功率不低于 Baseline。
- Advisory 必须降低每个成功任务的平均总 token，或者降低重复工具调用和无效 Agent step；仅降低主模型 token 不算通过。
- Provider 失败和 deadline 保持 fail-open，不阻塞主模型。
- 样本不足或结果波动时保持当前功能级别，不宣称已经节省 token。

本轮真实结果见[阶段六真实配对试点评估报告](./stage-6-real-pilot-report.md)。准确性非回归和安全条件通过，但成本与无效探索条件未通过；阶段六不能作为 Advisory 已产生产品价值或可以开发 Guided 模式的依据。

[真实失败 Session 筛选](./stage-6-real-failure-session-screening-report.md)进一步确认当前本机日志没有可用于稳定错误复测的合格案例，三个历史缺陷候选的六次有效 Baseline 也全部正确。后续评估必须先保留包含错误检查点和纠正证据的原始 Session，并使用最小代码切片和外部评分器控制筛选成本，再按 Baseline 稳定性条件决定是否调用 Jev。

真实用户纠正可通过 `/jev-failure <错误标签>` 显式采集。插件记录上一条 Assistant 检查点与纠正消息的本地引用，不复制正文、不调用 Jev，并按不同检查点去重；配置页在两个候选后显示配对测试就绪。评估人员仍需核验纠正证据和可重放条件，数量门槛不能替代案例资格审查。

## 总体验收条件

每个阶段依次运行相关单元测试，并在全部实现完成后运行：

```sh
pnpm test
pnpm eval
pnpm typecheck
pnpm build
git diff --check
```

最终还需要在真实 DSH Web 中验证配置保存、最近 Session 汇总、跳过原因、预算状态和 Advisory 注入。自动化测试通过但真实 Jev 配对数据不满足成本与成功率条件时，本计划只视为机制修复完成，不视为产品价值验收通过。

## 本轮不处理的内容

- 不通过降低置信度阈值提高表面注入率。
- 不恢复 fast、standard、deep 模型路由。
- 不允许 Jev 授权工具或其他外部操作。
- 不先开发新的图表面板；现有配置页只增加诊断所需的有限状态。
- 不根据两次或少量成功样本宣称 Jev 已提高准确率或节省 token。
